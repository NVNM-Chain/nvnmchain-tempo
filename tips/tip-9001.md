# TIP-9001: Staking Election, Weighted Proposers and Bound Fee Recipients

## Abstract

This TIP lets a staking contract named in genesis choose each epoch's committee among the validators registered in `ValidatorConfigV2`. From T12 it also draws block proposers in proportion to each validator's election weight, capped per seat, and makes a block pay only the fee recipient the registry holds for its proposer. Voting stays one vote per seat. A chain that names no staking contract keeps today's behaviour, except for the fee-recipient rules.

## Motivation

The NVNM whitepaper routes network fees three ways (protocol development, buybacks, validators), holds the validator share in a lockbox until the validator set votes distribution in, and at its last phase moves to delegated staking, where consensus rewards are distributed by stake weight rather than equally per seat (§5.1, §6.3, §6.6). The contracts that do the routing and the staking exist. Three things on the node side do not match them:

1. **The committee ignores stake.** The DKG players of the next epoch are every active entry of `ValidatorConfigV2`. A staking contract can rank candidates, but nothing reads its answer.
2. **Proposers are drawn uniformly.** Each seat proposes 1/N of the rounds, so each collects about 1/N of the fees whatever is staked behind it. With five seats, a token staked in a pool of 1M earns ten times what one in a pool of 10M earns.
3. **A validator can route its fees around the split.** A validator may set its own fee recipient, and a proposer may name any beneficiary. The fee split only holds if every block pays the validator's fee router.

Alternatives considered for the second point: leave proposers uniform and change the whitepaper; or redistribute by stake inside the contracts, which pays validators that are offline unless the node also reports per-validator block counts. Weighting votes as well is out of scope: it needs several threshold shares per validator and moves the halt threshold from a third of the seats to a third of the stake.

## Assumptions

- `ValidatorConfigV2` (TIP-1017) is the registry of consensus keys, staking addresses and fee recipients, and its owner is trusted to curate it.
- The staking contract answers `computeCommittee` and `electionWeight` deterministically from state, within the system-call gas limit. If it reverts, runs out of gas or answers badly, every node sees the same failure and takes the same fallback.
- The genesis fields this TIP adds live in the chain config, outside the genesis hash. Operators give every node the same values; nodes that differ compute different committees and fork at the next epoch boundary.
- Every validator runs a binary with this TIP before T12 activates. A binary without it stops at the first boundary outcome that carries proposer units rather than drawing different leaders.
- The epoch's DKG outcome in the boundary block header is the canonical source for the next epoch's players (TIP-1070).
- The consensus library exposes the leader elector as an extension point, and the threshold seed of a round is the same for every honest node.

# Specification

## Genesis configuration

Three optional fields in the genesis `config`:

| Field | Type | Meaning |
| --- | --- | --- |
| `stakingElection` | address | Contract whose `computeCommittee` selects each epoch's committee. Unset, the committee is the registry's active set. |
| `stakingElectionTime` | unix seconds | Block timestamp from which the election is used. Unset means from genesis. |
| `feeRouterFactory` | address | Contract whose `routerOf` mapping names the only fee recipient the registry accepts for a validator from T12. Unset, any non-zero recipient is accepted. |

A node MUST refuse to start on a genesis whose Tempo config fields are malformed, and MUST warn about each config key it does not recognize.

The node relies on this much of the contracts:

```solidity
interface IStakingElection {
    /// The committee for the next epoch, drawn only from `eligible`.
    function computeCommittee(address[] calldata eligible) external view returns (address[] memory);
    /// The election score of each address, elected or not. Zero for an address it does not rank.
    function electionWeight(address[] calldata who) external view returns (uint256[] memory);
}

// FeeRouterFactory: the fifth state variable, at storage slot 4.
mapping(address validator => address router) public routerOf;
```

## Committee election

The DKG outcome written in the last block of an epoch names `next_players`. The proposer of that block computes it from the post-state of the block's parent `P`, and every verifier recomputes it from the same state.

If `stakingElection` is unset, or `P.timestamp < stakingElectionTime`, `next_players` is the registry's active validators, as before.

Otherwise:

1. Let `registry` be the active entries of `ValidatorConfigV2` in contract order, skipping entries that do not decode.
2. Call `computeCommittee(eligible)` as a system call from the zero address, where `eligible` is the staking address of each registry entry in that order.
3. The elected committee is the registry entries whose address the call returned. Addresses outside the registry are ignored.
4. The committee is seated if it has at least `min(4, len(registry))` members and no duplicate keys.

If the committee is not seated — the contract has no code, the call reverts or runs out of gas, the return data does not decode, or the result is below the minimum — the node falls back, in order, to:

1. the players of the outcome being written that are still active in the registry, if they meet the same minimum;
2. the registry's active validators.

A failure that only this node observes, such as a failed state read, MUST abort building or verifying the block instead of falling back.

## Proposer units

From T12, where `stakingElection` is set, the boundary outcome also carries `proposer_units`: the odds of proposing for each player that runs the next epoch, in the order of the outcome's players. The gate is `P.timestamp`, the same block the election reads.

1. **Weights.** For each player key, look up its entry in the registry, deactivated entries included. The key is weighed at that entry's staking address only if the registry's current holder of the address has an index no greater than the entry's: a rotated key keeps its score until its successor holds a share, and a key whose address a later entry took, or that lost its address, is not weighed. Call `electionWeight` once with the weighed addresses. Before `stakingElectionTime`, or if the call fails or returns a different number of weights, no key is weighed.
2. **Units.** With `U = 10_000`, `units_i = max(1, floor(w_i × U / Σw))`. A key that is not weighed has `w = 0`. If `Σw = 0`, every unit is 1.
3. **Cap.** No seat may hold more than `CAP = 20%` of the units. Take the seats from the largest down; the `k` largest are set to `max(1, floor(CAP × rest / (1 − k × CAP)))`, where `rest` is the sum of the other seats, for the smallest `k` at which the next largest already fits. A cap below `1/N` is raised to `1/N`, which makes selection uniform.

Example: weights 30, 30, 30, 30, 5, 5 give shares of 20%, 20%, 20%, 20%, 10%, 10%.

## DKG outcome encoding

`OnchainDkgOutcome` gains `proposer_units: Option<Vec<u16>>`.

```
without units:  epoch | output | next_players | is_next_full_dkg (0 or 1)
with units:     epoch | output | next_players | 0x02 | is_next_full_dkg | units
```

A decoder MUST accept both layouts and MUST reject units whose count differs from the number of players in `output`. The marker `0x02` sits where a decoder without this TIP reads a boolean, so that decoder rejects the outcome.

## Leader election

Each epoch builds one elector from the outcome in the boundary block that precedes it.

- If the outcome has no units, the elector is the upstream one, in the version the boundary block's fork selects.
- If it has units, the participant at position `i` of the epoch's ordered key set gets the units recorded for its key, or 1 if none. View 1 is round robin, `(epoch + view) mod N`. For any later view, let `r = SHA-256(seed) mod Σunits`, where `seed` is the encoded threshold seed signature of the certificate that unlocked the view; the leader is the first participant whose cumulative units exceed `r`.

With equal units this is the upstream T12 schedule.

## Fee recipients

From T12, in `ValidatorConfigV2`:

- `setFeeRecipient` MUST revert with `Unauthorized` unless the caller is the registry owner. Before T12 the validator may also call it.
- `addValidator` and `setFeeRecipient` MUST revert with `InvalidValidatorAddress` if the recipient is zero.
- If `feeRouterFactory` is set, they MUST also revert with `InvalidValidatorAddress` unless the recipient equals the factory's `routerOf[validator]`, read from the factory's storage at `keccak256(abi.encode(validator, uint256(4)))`.

Recipients already registered when T12 activates are not changed, and genesis seeding is not subject to these checks.

From T12, in block execution: if the block names its proposer and the registry, initialized at or before the parent block, holds that key, the block's beneficiary MUST equal the fee recipient the registry held for the proposer at the parent block, a zero recipient included. Otherwise the block is invalid. The payload builder sets the beneficiary from the same lookup.

## Activation

- The election is a genesis setting, in force from `stakingElectionTime`.
- Proposer units and the fee-recipient rules activate with T12.
- The staking contract must expose `electionWeight` before T12; without it the committee is still elected and every seat draws alike.

## Open questions

- **`CAP`.** At 20%, a set of five or fewer draws uniformly, so weighting only shows from six seats. A cap that scales with the set, such as `2/N`, would bite earlier.
- **Weight formula.** The election score counts the validator's bond as well as delegated stake; using delegated stake alone equalizes yield per token across pools.
- **Chains without a staking contract.** The fee-recipient rules apply from T12 on any chain, so a node with this TIP no longer follows a network that activates T12 without them. They could instead apply only where `feeRouterFactory` is set.

# Tooling

- `tempo-xtask generate-genesis --fee-router-factory <address>` writes `feeRouterFactory`. `stakingElection` and `stakingElectionTime` are added to the config by hand.
- `tempo consensus set-validator-fee-recipient` works only for the registry owner from T12.
- No new RPC. The committee is read from the Current Committee state (TIP-1070), a block's proposer from its consensus context, and its fee recipient from the header's beneficiary.
- Operators upgrading a running network set the new config fields and `t12Time` on every node and restart before `t12Time`.

# Observability

No new on-chain events: the staking and router contracts emit their own. The node logs each decision at the boundary:

| Log | Level | Answers |
| --- | --- | --- |
| `next committee elected by staking contract` | info | Was the election used, and how many seats? |
| `election fell back to the current players` / `next committee is the full registry` | info | Which fallback was taken? |
| `election contract has no code; falling back`, `election call did not succeed; falling back`, `elected committee below minimum; falling back` | warn | Why did the election not seat a committee? |
| `electionWeight answered badly; every proposer draws alike` | warn | Why are proposers uniform? |
| `genesis config key is unknown to Tempo and ignored` | warn | Is a config field misspelled or from another version? |
| `our public dkg outcome does not match what's stored in the block` (with both outcomes' `proposer_units`) | warn | Do nodes disagree on the committee or the units? |

Whether weighting is in effect is visible in the boundary header: the outcome carries units or it does not.

# Threat Model

- **Registry owner**: trusted to curate validators and, from T12, to set every fee recipient. It can point a recipient anywhere unless `feeRouterFactory` is set, and can then only choose among routers the factory created for that validator.
- **Staking contract owner**: controls an upgradeable contract whose answers seat the committee and weigh proposers. It cannot seat a key outside the registry, cannot shrink the committee below `min(4, registry)`, and cannot give one seat more than `CAP` of the proposals. It can, within those limits, decide the committee.
- **Validators and proposers**: untrusted for fees. From T12 a validator cannot redirect its own fees and a proposer cannot pay another beneficiary.
- **Heavy validator**: proposes more blocks and has more chances to censor or reorder, bounded by `CAP`. If it is offline, its share of rounds waits for the leader timeout.
- **Election contract failure**: in scope. A revert, missing code, exhausted gas or malformed answer is the same on every node and leads to the deterministic fallback, never to invented weights.
- **Node with an older binary**: in scope. It rejects the first outcome with units and halts instead of following a different leader schedule.
- **Mismatched genesis config across nodes**: out of scope for the protocol; it forks the network and is prevented operationally.

# Invariants

- The proposer and every verifier of a boundary block compute the same outcome from the parent's post-state and the ceremony output.
- `next_players` is a subset of the registry's active keys, with at least `min(4, len(registry))` members whenever the registry is not empty.
- `proposer_units`, when present, has exactly one entry per player, each at least 1, and no entry exceeds `max(CAP, 1/N)` of their sum.
- An outcome carries units only if `stakingElection` is set and T12 is active at the parent block.
- Every node that starts an epoch builds the same elector from the boundary header alone, including a node restored from a snapshot.
- From T12, a block whose proposer the registry knows pays exactly that proposer's registered fee recipient.
- From T12, only the registry owner changes a fee recipient, never to zero, and with `feeRouterFactory` set only to `routerOf[validator]`.
- A fallback never assigns unequal units.

The test suite must cover:

- The election: a seated committee, each failure mode falling back, the minimum with small registries, the activation time, and the registry passed in contract order.
- Weights: a key weighed at its staking address after rotation; a key whose address was taken over or transferred away; a contract without `electionWeight`; a short answer.
- Units and cap: proportionality with a floor of one, zero weights, weights at the top of `uint256`, a cap that reaches several seats, a cap below `1/N`.
- Encoding: round trip with and without units, a decoder without units rejecting an outcome with them, a unit count that does not match the players.
- The elector: round robin at view 1, the hashed draw, leader counts following units over many seeds.
- End to end: a signer weighed at zero stops proposing once outcomes carry units and keeps proposing before T12; proposer counts track stake on a network that crosses T12; a committee shrinking after a candidate is removed.
- Fee recipients: owner-only and non-zero from T12, the router check, a block with a foreign beneficiary rejected from T12 and accepted before it.
